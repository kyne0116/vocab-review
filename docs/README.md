# vocab-review 文档管理说明

`docs/` 是本项目的开发文档真相源；使用手册（运行、发布、功能说明）见根目录 `README.md`，不在此重复。本文只维护文档地图和规则，不复制各正本内容。

## 目录边界

| 目录 | 保存内容 | 不保存内容 |
|---|---|---|
| `产品方案/` | 产品概述与需求目标、产品方案正本、技术选型结论、ADR | 日常进度、临时排查、未确认方案 |
| `开发过程/` | 阶段状态、当前任务、待拍板议题、完成记录 | 正式需求、正式架构、接口与数据设计 |
| `运维手册/` | 代码之外的微信平台侧配置：mp 后台 / 开发者工具 / 真机操作手册与踩坑记录 | 产品方案、开发过程状态类内容（使用手册仍在根 `README.md`） |

## 阅读顺序

1. `产品方案/00-产品概述与需求目标.md` —— 项目定位、功能现状、当前需求
2. `产品方案/01-拍照收词产品方案.md` —— 当前特性的产品与整合设计（R01–R04 已拍板确认）
3. `产品方案/02-技术选型与验证.md` 与 `产品方案/adr/` —— 选型对比、已验证事实、正式决策
4. `开发过程/` —— 当前阶段、开放任务、待拍板议题、已完成事实
5. `运维手册/` —— 代码之外的微信平台配置、操作路径与踩坑记录（发布 / 真机验证前常查）

## 文档规则

1. 未确认内容只保留在当轮讨论或 `开发过程/`（当前任务 / 待拍板议题），不得提前写成正式结论。
2. 用户确认后，直接更新所属正本，不创建「最终版」「最新版」或 V2 副本。
3. 技术分析区分 `事实`（已验证）、`推断`、`建议` 和 `待验证`。
4. 重大且长期有效的技术选择使用 ADR；普通选择直接写入所属正本。
5. 代码、配置和自动化测试（`test/test-logic.js`）是系统实际行为的执行真相，正本应能引用实现或验证证据；未实现内容不得使用「已支持」「已完成」等终态措辞。
6. 每轮变更在同一轮完成对账：当前任务 → 用户确认 → 正本 → 代码/测试 → 验证 → 完成记录，任务完成后从当前任务删除。

## 议题确认方式

每次只讨论一个议题（可一次回复多个编号）。固定包含：议题内容、可选方案、推荐方案、推荐理由、影响、待确认问题。确认回复建议使用 `R01=A` 这样的格式。只有明确确认的结论才进入正式正本。
